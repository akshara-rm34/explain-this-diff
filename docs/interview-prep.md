**Q1.** The new source map pattern is /\.(js|css)\.map$/ rather than a plain /\.map$/. Why restrict it to js and css maps, and what could go wrong with the broader pattern? <sub>`src/diff.ts`</sub>

> I only wanted to skip bundler output. .js.map and .css.map are generated by build tools and are just huge JSON blobs of mappings, so they waste the diff budget. A plain .map pattern is too broad because .map is also used for real files, like nginx map configs, linker map files, or game/tile map data, and those could be meaningful changes. One gap: TypeScript's declaration maps (.d.ts.map) aren't covered by this pattern.

*Feedback (solid):* You gave the key reason: plain .map would also catch real files like nginx map configs, linker maps, and tile data, while .js.map and .css.map are bundler output. You also flagged the real gap, that .d.ts.map isn't matched by this regex.

*Stronger answer:* A plain .map rule would also skip legitimate files like nginx map configs, linker maps, or tile data, so I scoped it to .js.map and .css.map, which bundlers generate and which are large mapping blobs that eat the diff budget. It's a deliberate tradeoff. The known gap is TypeScript declaration maps (.d.ts.map), which this pattern doesn't match, so I'd add them if they show up as noise.

**Q2.** NOISE_PATTERNS is checked in order, so the first matching pattern supplies the skip reason. Why were the new source map and generated types entries placed before the binary and snapshot entries, and does that ordering change any result? <sub>`src/diff.ts`</sub>

> The order doesn't change any result for these entries. A file ending in .js.map or .d.ts can't also end in .png or .snap, so the patterns don't overlap. I put them next to the minified rule just to group the "generated text file" rules together. *Feedback (solid):* Correct: none of the non-build patterns can match a .js.map or .d.ts file, and the build output rule runs first, which is why dist/app.js.map reports as "build output". You also made clear that the order only changes the reason label, not whether the file is skipped.

*Stronger answer:* The order doesn't change results for these entries because no other non-build pattern can match a .js.map or .d.ts file. The only overlap is with the build output rule, which runs first and labels dist/ files as "build output" instead. The skip decision is the same either way, so placement here is about grouping the generated-text rules together.

**Q3.** Dropping every .d.ts file also drops hand-written declaration files, such as global augmentations or ambient module typings in a library. What did you weigh against that cost, and would a path-based rule like types/ or dist/ have been safer? <sub>`src/diff.ts`</sub>

A better approach would be to only skip .d.ts files inside build folders, or when the matching .ts source is in the same diff. I'd probably drop the .d.ts rule and keep just the source map one.

However, you missed that the PR's own test asserts types/index.d.ts is skipped, a non-build path your proposed fix would change, and the claim that generated declarations usually land in dist/ isn't supported by the diff.

*Stronger answer:* The rule as written is broad: it drops any .d.ts, including hand-written ones like global.d.ts or env.d.ts, and the new test even locks in skipping types/index.d.ts, which isn't in a build folder. Generated declarations usually sit under dist/ or build/, which the existing build output rule already skips, so I'd either narrow this rule to .d.ts files under those folders or drop it. If I narrow or drop it, I'd update the test to match, and I'd check how this repo actually emits declarations before deciding.
